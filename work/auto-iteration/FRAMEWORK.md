# AutoIteration Framework

## 1. 定位

AutoIteration 是以长期策略目标为中心的研究循环：读取规则和设计意图，发现策略
与目标之间的缺口，提出可证伪的假设，用可比证据验证，再决定是否更新工作基线。

它不等同于“修改代码、跑一批局、看胜率”。胜率是最高层结果指标，但过程指标可以
在没有立即提升胜率时证明策略能力正在接近长期目标。具体过程指标不写死在本文件，
由 `metrics/` 下的 active profile 提供。

## 2. 目标、行为、证据、结论

每轮必须回答四个问题：

1. 我们原本想让策略实现什么长期目标？
2. 当前证据表明策略在哪个环节偏离目标？
3. 候选改动为什么有机会缩小这个偏离？
4. 这次改动是否在可接受代价下让策略更接近目标？

记录中严格区分：

- **事实**：具体局面、合法选项、动作和结果；
- **解释**：对事实的原因分析；
- **假设**：改变某个行为后预期出现的可观测变化；
- **结论**：在预先约定的证据标准下支持、保留或否定假设。

不能把候选版本胜率上涨直接写成策略改动有效，也不能把没有资源直接写成 agent
做错了。

## 3. 规范来源和经验来源

### 规范来源优先级

出现冲突时按以下顺序处理：

1. 官方规则和卡牌事实；
2. 项目已确认的规则报告和策略设计原则；
3. `GOALS.md` 中的长期目标；
4. 当前 agent 的实际行为；
5. 单次实验结果或未经复核的直觉。

低优先级结果不能推翻高优先级规则。若实现行为与规则或设计意图冲突，先记录冲突
和证据，再决定是否提出策略假设。

### 经验来源回答的问题

| 来源 | 能回答的问题 | 不能单独证明的事情 |
| --- | --- | --- |
| 规则/设计文档 | 什么方向才是正确目标 | 真实对局收益 |
| 单局 case/replay | 错误发生在哪个局面 | 普遍提升 |
| focused evaluation | 目标行为是否按机制改变 | 完整 matchup 收益 |
| full control/candidate | 固定范围内是否有可重复影响 | 所有外部环境的长期价值 |
| 官方 Kaggle 对局 | 真实环境中的长期结果 | 某个内部改动的单独因果 |

## 4. 单轮生命周期

### Phase 0：建立上下文

固定并记录：

- `iteration_id`、control 和 candidate 引用；
- 卡组状态和版本标识；
- 当前长期目标；
- active metric profile；
- 评测器、分析器和评测配置版本；
- 上一轮未解决的问题。

### Phase 1：定义目标和缺口

从目标文档和历史结论开始，不从某个新数字开始。说明：

- 目标希望策略最终具备什么能力；
- 当前缺口如何影响完整策略路线；
- 缺口是普遍问题、特定情形问题，还是尚未证实的问题。

如果当前路径理论上无法达到目标，必须提出至少一个替代路径，并比较资源、时机和
风险，而不是只在原路径上继续调整排序。

### Phase 2：问题归因

每个主要问题选择一个归因：

| 类别 | 含义 | 默认处理 |
| --- | --- | --- |
| `rule_error` | 违反官方规则或卡牌文本 | 先修复规则理解和合法性 |
| `strategy_miss` | 合法且可达，但 agent 选择了较差动作 | 提出策略假设 |
| `unavailable` | 目标动作或资源当时不可达 | 不计为策略漏做，研究机会条件 |
| `unavoidable` | 在当前资源和规则下无法避免 | 记录边界，不强行修复 |
| `measurement_error` | 事件、分母或归因识别错误 | `measurement_only`，先修复测量 |
| `outcome_only` | 只有结果变差，没有行为证据 | 先寻找可归因 case |

“没有形成目标状态”不能自动等同于“agent 没有选择正确动作”。

### Phase 3：提出一个主要假设

每轮只能有一个驱动 candidate 和 promotion 的主要假设。它至少说明：

- 服务哪个长期目标；
- 当前行为缺口；
- candidate 改变的一个决策或边界；
- 预期机制和目标信号；
- 可能损害的既有能力；
- 替代路径；
- 证伪条件。

其他指标可以作为健康检查或后续研究线索，但不能在看到结果后临时升级为主要目标。

### Phase 4：预先写评测计划

在运行 candidate 前固定：

- active profile 中的目标指标和分母；
- correctness gate；
- focused 情形；
- full 对手范围、局数、先后手和随机性策略；
- 结果护栏；
- 通过、观察和失败条件。

指标定义、分母或事件识别方式在运行后改变时，必须标记为测量版本变化，不得和旧
口径直接比较。

### Phase 5：Correctness gate

先确认候选和评测链路可信：

- 只返回模拟器提供的合法动作；
- 没有 agent 崩溃或未处理异常；
- 没有跨局状态泄漏；
- control 和 candidate 遵守相同的运行时契约；
- 分析器能可靠识别目标事件、分母和错误归属；
- 打包和入口没有回归。

gate 失败时不能由胜率或过程指标抵消。若失败来自测量或运行环境，标记为
`measurement_only` 或暂停策略判断。

### Phase 6：Focused evaluation

focused 只回答机制问题：目标情形是否出现、candidate 是否做出预期行为、行为是否
符合假设、是否出现直接副作用。

focused 可以使用最小 fixture、少量高相关情形或特定对手范围，但必须明确标记。它不
能单独替代 full comparison，也不能把 focused 胜率与 full batch 胜率直接比较。

### Phase 7：Full comparison

control 和 candidate 尽可能固定：

- 卡组、规则、评测器和分析器版本；
- 对手矩阵、每个对手的局数和先后手策略；
- 随机性、重复批次和停止条件；
- active profile、分母和异常归属。

如果使用独立随机批次，必须明确不是逐局配对，并通过重复批次和不确定性解释结果。
卡组、评测器或指标定义发生变化时，必须更换迭代类型或比较基线。

### Phase 8：外部验证

候选通过本地研究门槛后，再用官方 Kaggle Episode/replay 观察外部长期价值。外部
结果不能替代行为归因，必须记录版本、对手、样本、异常终局和仍无法推出的结论。

### Phase 9：解释和决策

如果 active profile 声明了优先级，必须按优先级从高到低解释；低优先级过程指标或惩罚项
的改善不能抵消高优先级结果和核心能力的未解释回退。profile 的具体顺序不写死在通用
框架中，但必须在运行前固定并写入 iteration 记录。

按以下顺序解释结果：

1. active profile 的目标信号是否按机制改善；
2. 核心健康能力是否回退；
3. 胜率及先手/后手结果是否出现不可接受回退；
4. 哪些变化不能归因于本轮改动；
5. 下一轮最小研究问题是什么。

## 5. 决策状态

### `promote`

correctness 通过、比较口径有效、主要假设得到支持、没有不可接受的核心健康或结果
回退，并且证据足以让 candidate 成为下一轮 control。

`promote` 只表示当前证据支持更新工作基线，不表示候选已经在所有对手和场景下最优。

### `observe`

目标情形有改善但样本不足、full 不可比、健康信号混合、外部验证缺失或测量刚修复时，
使用 `observe`。下一轮必须指定扩大样本、修复测量、收窄条件或测试替代路径。

### `reject`

主要假设在可达机会中没有改善、机制被反驳、引入硬错误，或造成无法接受的核心/结果
回退时使用 `reject`。失败原因必须进入下一次假设，不能只换版本号。

### `measurement_only`

只改变分析器、trace 解析、事件分类、分母或报告格式时使用。它可以提升我们对策略
的认识，但不能声称策略行为提升，也不能用新旧不同口径直接晋级。
