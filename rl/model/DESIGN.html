BC checkpoint 可以作为 RL rollout policy 的起点，但当前 value head 没有被 BC loss 训练，不能直接当成可靠的 value function。

因此“接口能衔接”是对的，“训练结果已经自动衔接完成”还需要补上 rollout、reward、advantage/value 和合法 action mask 的工程合同。

02 / Input contract

模型究竟看到了什么

字段不是原始 JSON 的简单复制，而是一个固定 versioned encoder。卡牌 ID 使用 embedding，连续量统一做简单归一化。

状态数值：46 维
14 · resources / board10 · turn / selection8 · logs4 · action history4 · effect context6 · timing

包含双方 Prize、牌库数量、手牌数量、弃牌数量、Bench 数、Active HP/能量；当前回合、先后手、Supporter/Energy/Retreat 状态；select type/context/min/max；最近日志；最近 32 个 main action 的最后摘要；effect/context card；turnActionCount、appearThisTurn 等合法时机信号。

卡牌状态 token：40 个 ID
己方 Active + Bench · 6对方 Active + Bench · 6己方手牌 · 16己方弃牌 · 8对方弃牌 · 4

所有 token 都是 card ID，不是卡牌文本或图像。0 是 padding，真实 ID 会加 1。对方手牌内容不可见，所以不编码具体 opponent-hand cards，只保留公开的 handCount。

候选动作：每个 option 的 13 个输入字段
type idvisible card idtarget card id10 numeric

numeric 字段是候选 index、area、inPlayArea、index、inPlayIndex、attackId、number、select type、select context、maxCount。v6 会从公开手牌/场上/弃牌/搜索区域解析 action_card_ids 和 action_target_ids。

最近动作和 effect memory：有限状态，不是 RNN

数据构建器会把同一玩家最近最多 32 个 main action 的 type/card/attack 摘要放进 rl_history；effect selection 使用 effect serial 计步。运行时由 policy 自己维护这段 history，所以它不是 Transformer 跨整局记忆。

合法性边界：mask 来自 simulator

真实 options 的位置标记为 true，补齐到 64 的 padding 标记为 false。训练和推理都只能在这组 options 上选；模型本身不会产生全局 action ID，也不会绕过 minCount/maxCount。

明确没有输入的东西
对手隐藏手牌内容牌库顺序未知 Prize 内容卡牌文本语义反事实 outcome

这不是缺陷清单，而是信息边界。若训练目标需要判断隐藏牌分布或动作的未来收益，必须通过 belief/determinization、value/advantage 或额外的搜索数据补充。

覆盖性判断

把输入按模型能否回答的问题分成三层：

  • 已覆盖
    当前场面、资源、可见卡牌、回合合法性、当前合法候选动作。
  • 部分覆盖
    短期时序：最近动作摘要和 effect step 有，但不是完整事件/长期记忆。
  • 未覆盖
    对手隐藏信息、动作之后的反事实收益、卡牌文本组合语义。

04 / BC objective

当前 BC 学的是什么

每条样本的 label 是当前 options 中的 index set，不是跨牌局固定的 action ID。single、multi 和 empty selection 使用同一个候选集合合同。

单选：masked CEtarget_count = 1 时，在合法 logits 上分类。
多选：candidate BCE对合法 candidates 做 multi-label binary loss。
数量：count CE预测 0..64，训练和推理都限制在 minCount..maxCount。
h_state = LayerNorm(pool(Transformer(card_tokens)) + MLP(state_numeric))
h_i = E_type + E_card + E_target + MLP(action_numeric_i)
logit_i = Policy([h_state ; h_i])
count = CountHead(h_state)

L_policy = CE(logits, target) if |target| = 1
        = BCE(logits, target_mask) otherwise
L_total = L_policy + CE(count_logits, target_count)

05 / Training stage

BC → RL：你的理解哪里正确

用按钮切换两个阶段。页面把“接口连续性”和“训练目标变化”分开，避免把 BC checkpoint 误称成已经完成 RL。

数据 已完成合同

Kaggle replay 的 observation[i] 与下一行的 action 对齐，编码成 v6 JSONL。

  • 完整 episode 切分 train/validation/test
  • 保留合法 options 和 target index set
  • 当前最新 exact-deck pool：173,251 records

训练 当前

随机初始化的 full-action policy 训练 20 epochs，AdamW，batch 256，learning rate 3e-4。

  • policy + count loss
  • 无 reward shaping
  • 无 teacher fallback / search fallback

产物 可 rollout

checkpoint 能加载同一 feature/model contract，并对真实 observation 执行 deterministic inference。

  • 输出仍受 simulator candidate mask 约束
  • 可用于生成候选 agent rollout
  • value head 尚不是可信的 value function

Rollout

用 BC policy 在 simulator 中真实推进对局，保存每个 decision 的 state、合法 options、action、log-prob、mask 和 next state。

  • 必须在同一 action contract 内采样
  • 不能只保留最终胜负

Reward / advantage

根据终局胜负、可见势能或经过验证的 transition reward 计算 return，再用 value baseline 得到 advantage。

  • terminal reward 可以很稀疏
  • 需要处理 hidden information 与 episode perspective

PPO update

冻结 old policy 计算 old log-prob，在合法 candidate mask 内做 clipped ratio 更新，同时训练 value head。

  • rollout policy 与更新模型必须 shape 对齐
  • 更新后回到固定 evaluation 护栏

你的理解：核心方向正确

BC checkpoint 确实可以作为下一阶段 RL 的 policy 初始化。它可以加载后在官方 simulator 中做真实推理、生成 rollout，然后用 rollout 中的状态转移和结果构造 reward，再进行 PPO-style policy/value 优化。

需要补上的条件：不是“直接无缝”

当前 BC 的 value head 没有训练，BC 数据也没有 old log-prob、advantage 或可靠的 transition return。进入 PPO 前，需要补齐 rollout schema、reward profile、value calibration/训练、masked log-prob、GAE/return 和 checkpoint 评测护栏。

下一步讨论重点

如果目标是判断 observation 是否够用，优先看三件事：哪些失败来自缺少隐藏信息、哪些失败来自没有长期记忆、哪些失败来自没有反事实收益。只增加字段不能自动解决后两类问题；它们分别需要 memory/state design 与 value/advantage/search data。
