Experiment observability design · 2026-07-25

让 BC 与 RL 的“状态好坏”
真正可比较

面向 Pokémon TCG policy learning 的 W&B 记录方案。重点不是一次堆满指标，而是先建立稳定的 run 身份、冻结评测合同和轻量云端比较层，让以后每次 BC、value calibration、PPO 更新都能回答：它比上一个可比状态更好吗？

结论：建议采用免费额度优先JSONL 仍是事实源TensorBoard 继续保留官方 engine evaluation 才判定强度
结论免费权限架构Run 身份指标合同比较规则页面设计成本与隐私落地阶段资料来源

01 · 建议结论

采用“一份本地事实，两种可视化，一个冻结裁判”

每个仓库版本只产生一份 canonical JSONL；同一条记录镜像到 TensorBoard 和可选的 W&B。TensorBoard 服务单机实时曲线，W&B 服务跨版本筛选、分组、并排比较、小型 Tables 和阶段报告。最终策略强弱只读取官方 engine 的固定 evaluation 结果。

Canonical
JSONL

逐 epoch / update 的事实记录；断网、SDK 故障或账号变化都不能影响它。

Live local
TensorBoard

继续快速查看本机训练曲线，不改变当前工作习惯。

Compare & report
W&B

把不同 V 按阶段、配置与冻结评测汇总，提供可过滤的远程实验视图。

BC loss 与 PPO policy loss 没有共同语义，不能放在一条“谁更强”的曲线上。BC 和 RL 真正共用的比较面是：同一评测合同下的胜率、完成率、错误率、先后手表现、对手分解和资源成本。

05 · 指标合同：先少而稳，再逐步丰富

P0 决定 policy state 是否更好；P1 判断训练有没有坏；P2 才解释为什么。第一阶段只要求 P0 + 少量 P1 完整可靠。

P0 · Comparable outcome

跨 BC / RL 共用

固定官方评测的胜率、完成率、错误率、先后手、对手分解和置信区间。

P1 · Training health

阶段内监控

合法动作、梯度、KL、吞吐、loss、entropy；不能单独宣称策略更强。

P2 · Diagnostics

按需采样

动作类别、opponent case、校准分桶、失败类型；用小表或本地报告。

P0：共享 frozen evaluation summary

指标含义方向
eval/outcome/win_rate固定矩阵总体胜率越高越好
eval/outcome/win_rate_ci_low/high建议 Wilson 95% 区间辅助判断不确定性
eval/outcome/completion_rate正常完成局数 / 总局数越高越好
eval/outcome/error_rateengine / worker / policy error 比例越低越好
eval/outcome/games真实官方 engine 对局数样本量
eval/seat/first_win_rate先手胜率分层观察
eval/seat/second_win_rate后手胜率分层观察
eval/quality/illegal_action_rate策略非法动作率必须为 0
eval/quality/avg_complete_turns官方最终 turn 的 ceil(turn/2)解释节奏

阶段自定义横轴核心指标用途

禁止制造“统一总分”。 第一阶段不把胜率、loss、吞吐和完成率加权。晋级采用护栏：官方胜率有改善证据，同时完成率不降、非法动作率为零、error / step-limit 受控。

06 · 哪些数据可以比较？

比较允许？理由
BC V4 vs PPO V1 的固定官方胜率允许evaluation contract hash 必须完全一致
BC train loss vs PPO policy loss禁止目标函数、尺度、采样分布不同
两个 BC 的 validation exact action rate有条件dataset manifest、split、teacher/source、schema 一致
两个 PPO 的 approx KL有条件action contract、batch 与聚合定义一致
rollout win rate vs frozen eval win rate禁止opponent sampling 与用途不同
不同 opponent catalog 的总体胜率禁止测试难度变化会冒充策略变化
相同模型、不同 workers 的吞吐允许只形成性能结论，不形成强度证据

每个可比点必须携带

  • 官方 engine runtime / build hash；绝不修改 engine/source/。
  • opponent catalog hash、每对手局数、seed schedule、先后手轮换。
  • candidate / checkpoint hash、metric profile ID 与 revision。
  • workers、worker CPU threads 和错误统计；并行度只解释耗时。
  • 真实 report path、report hash 与 run_id；W&B 不复制或伪造正式报告。

07 · W&B 页面设计

Workspace 1

Policy Scoreboard

默认只显示同一 evaluation contract：版本、stage、parent policy、胜率与 CI、完成率、错误率、先后手、局数、耗时、promotion status。

Workspace 2

Training Health

按 job_type 分为 BC、value、PPO 三组，禁止把不同目标的 loss 画进同一 panel；另设 system throughput 区。

Table

Frozen Evaluation Breakdown

每个 opponent × seat 一行，保留 games、W/L、win rate、completion、errors、turns，不上传逐 decision observation。

Report

Version Decision

固定模板：假设 → 改动变量 → 训练健康 → frozen evaluation → regressions → 决策 → 下一版本，并链接仓库正式 HTML。

Run Comparer 官方当前默认展示前 10 个可见 runs；先按 job_type、contract hash、stage、status 过滤，再打开 Diff only。Parallel Coordinates 与 Parameter Importance 只用于形成假设，不提供因果结论。

08 · 免费额度、隐私和数据量护栏

上传

  • 有限频率标量
  • config / summary / hashes
  • 紧凑 opponent 表
  • 小型状态与决策文本

本地保留

  • checkpoint / optimizer
  • dataset / 完整 manifest
  • trace / replay / frames
  • 正式 evaluation HTML

内部预算

  • 单 run ≤ 10k history rows
  • 单 Table ≤ 200 聚合行
  • 单版本文件 ≤ 10 MB
  • 月平均目标 < 1 GB

以上是本项目主动护栏，不是 W&B 官方 API 上限；目的是长期留出免费额度余量。

风险默认防护
API key 泄露只使用 WANDB_API_KEY；不得写入 config、日志、Git 或 HTML
console 泄露内容WANDB_CONSOLE=off；只上传白名单字段
source patch 自动上传WANDB_DISABLE_CODE=true；commit/hash 由 manifest 记录
默认目录污染WANDB_DIR 指向版本隔离目录并保持 Git ignore
网络中断训练JSONL 先写；sink 捕获 import/init/log/finish 异常并降级
误用云端当永久归档checkpoint 与 evaluation HTML 仍按仓库契约长期保存
容量被二进制吃光默认禁止 run.log_model；只记本地路径和 SHA-256
本项目已在 2026-07-26 完成一次授权的 online synthetic smoke，并通过 API 确认 project access 为 PRIVATE。后续正式训练直接使用 online scalar mirror；offline 仍用于无网络诊断，且不得把未检查的离线目录批量同步到正式项目。

09 · 分阶段落地，不追求一次做满

0

设计冻结（本文件）

确定 JSONL 权威性、run 身份、metric namespaces、evaluation contract 与禁止上传清单。

1

Scalar mirror + online smoke（已完成）

TrainingLogger 已增加 failure-isolated sink；BC 与 PPO 只传有限标量。5 epoch online smoke 已回读 5 行 history 和 6 条序列，仅同步 4 个 W&B metadata/config 文件，0 media、0 artifact。查看验证 run。

2

Frozen evaluation summary

正式报告生成后写 eval/* 和 compact Table，完成 Policy Scoreboard；这是比较不同状态的第一项真正收益。

3

Version Decision Report

每次晋级或拒绝留下假设、变量、护栏、结果和下一步；引用本地正式 HTML。

4

最后再考虑 Sweeps

只有合同稳定、单次成本可控、积累一批同口径 runs 后，才启用 parameter importance 或有限 Sweeps，避免 evaluation 泄漏。

Phase 1 验收（2026-07-26 通过）

  • 未安装 SDK 或 disabled 时，现有训练与测试行为不变。
  • JSONL 先于 W&B；模拟网络错误不丢记录、不终止训练。
  • 同一 V 恢复相同 ID；新 V 不能覆盖旧 run。
  • BC 与 PPO 使用各自自定义横轴。
  • 云端无 API key、checkpoint、trace、replay、observation、source patch。
  • 正式比较只显示相同 evaluation contract hash。
  • 实现同步更新 train/alakazam_bc_rl/DESIGN.html 与运行说明。

具体实施步骤见 W&B BC/RL Experiment Tracking Implementation Plan。
