0015 · 多龙构筑条件化 BC

前瞻实验：用纯多龙补充“多龙模块”，用宝石海星 + 黑夜魔灵补充“黑夜魔灵模块”，检验二者能否在自爆多龙目标构筑上形成可测量的组合迁移。

prospective · 未训练BC-firstT0–T3 component transfervalue / RL deferred
0014 审查结论：AC/R1 足以表达完整 60 张初始构筑；A0 不足。
现有 V9 已证明构筑通路接通且 logits 对卡牌数量变化敏感，但尚未证明跨构筑的正确泛化。

01 · 要组合的不是三套完整策略，而是两个子模块

纯多龙多龙铺场、能量、前后场轮转、Phantom Dive 提交与伤害分配
宝石海星 + 黑夜魔灵Duskull 铺场、进化、Cursed Blast 时机、目标和自爆后接力
→
目标：多龙 + 黑夜魔灵在 exact own-deck 条件下组合两个模块；最终只在目标构筑留出数据和目标 candidate 上判定收益。

宝石海星的攻击几何和能量路线不同，因此它只提供可能复用的黑夜魔灵监督。不能因混合数据总准确率上升就声称迁移成功。

02 · 0014 的 registered-deck 能力审查

层级结论0015 含义
Cache / compiler支持registered_card_ids + registered_multiplicity 可无损还原 60 张 multiset。
AC / R1支持registered cards 与资源账本进入 resource/scenario memory，并条件化 state 与 legal options。
Online / export支持实际 candidate 的 deck.csv 被校验为 60 张并进入同一编码合同。
A0不支持没有消费 registered-deck 特征，不能作为本实验架构。
广泛泛化证据尚无0014 只有一张卡差异的两个不平衡签名，不能代表三 archetype。

已有 cache

162,128 decisions；两个签名占比 85.7% / 14.3%，仅 Enhanced Hammer 与 Nighttime Mine 的 4/2、3/3 互换。

V9 sensitivity

固定同一 validation state，只改 multiplicity：finite-logit max Δ = 0.1878586，mean Δ = 0.0823456。

正确解读

证明“有线且模型在用”；不证明变化后的动作正确，也不证明它能理解纯多龙、目标多龙和宝石海星的差异。

03 · 模型和信息边界

π(a | s, D) s = action-time actor-visible board/history + legal full-action options D = exact registered own 60-card multiset allowed: own deck identity/counts, ontology, known zones, bounded/unknown resource ledger audit only: build family, deck hash, expert/team source, outcome forbidden live inputs: future frame, terminal result, opponent hidden deck, expert identity

采用 0014 AC/R1 风格的 registered-card memory；保留卡牌 identity、初始 multiplicity 和当前资源位置。不同构筑/来源不能无条件混标签。source 用于 manifest、平衡采样和分组报告，默认不作为策略输入。

04 · 受控 T0–T3 实验矩阵

Arm训练数据它单独回答什么
T0仅多龙 + 黑夜魔灵稀缺目标数据自身的 BC baseline。
T1T0 + 纯多龙多龙进攻/轮转模块是否迁移。
T2T0 + 宝石海星 + 黑夜魔灵黑夜魔灵铺场、进化、自爆模块是否迁移。
T3三者全部两个辅助模块是否互补、可组合且没有负迁移。
T3-no-deck同数据、同 updates，mask exact deck收益是否真的依赖构筑条件，而不只是样本更多。
竞赛导向的数据合同：不做人为 50/50，也不为了学术归因丢掉可用对局。T0 使用全部合格目标数据；T1/T2 在 T0 上加入对应来源的全部合格数据；T3 使用三者完整并集。每 epoch 每条选中 decision 学一次，因此 T1–T3 天然 updates 更多、耗时更长。结果诚实解释为 data + compute 的实际增量；仍按整局切分并禁止泄漏、重复和构筑误标。

05 · 失败对局如何进入 BC

可以使用

数据稀缺时保留经审计的完整失败局；失败是 episode metadata，不代表每一步都错。

暂不做 value

不把终局胜负复制为逐动作 reward/value target，也不假装定位了关键失误。

可控的静态权重

只有出现噪声压制时，比较 bounded episode/source quality 权重；始终另报 unweighted validation 和各 strata 有效权重。

06 · 唯一成功目标：自爆多龙

评测收口：没有可在本地运行的老师 policy，因此不存在“学生对老师胜率”。纯多龙和宝石海星 + 黑夜魔灵只提供辅助训练数据与诊断，不进入 checkpoint 排名、headline score 或最终 go/no-go。T0–T3 的成功只由我们自己的版本在同一套“多龙 + 黑夜魔灵”目标构筑上的相对变化决定。

离线一致率：诊断轴

只看目标构筑 holdout，判断对老师 logged states 的复现、是否明显学歪，并用同一预声明规则为各 arm 选择 checkpoint。

Official-engine：强度轴

所有 frozen candidate 使用同一目标 deck.csv。真实 W/L/error 是主要终点，因为它评估模型自己行为所诱导出的局面。

动作一致率下降、真实胜率上升并不矛盾：多个动作可能近似等价，辅助数据也可能改善 teacher holdout 很少覆盖的恢复局面。它是有价值的候选结论，但必须由冻结 package 的新 seed 确认，而不是一次点估计。

08 · 二维结果怎么解读

目标构筑一致率目标构筑真实强度结论
上升上升最干净的正迁移。
下降上升可能学到了超越字面模仿的稳健策略；冻结模型新 seed 复现后可视为成功。
上升持平/下降更像老师，但没有更强的实战证据。
下降下降负迁移或确实学歪。

T3 ≈ T3-no-deck 时，只能说辅助数据可能有效，不能说 exact-deck conditioning 已被证明。

09 · 不泄漏的真实对战合同

每 epoch 做目标构筑完整固定 validation，不做大型 engine tournament，也不根据 engine 胜率挑 epoch。所有 arm 使用同一目标-only 离线规则各冻结一个 checkpoint，再导出同一套目标多龙 + 黑夜魔灵 deck.csv。另外按预声明的首个、25%、50%、75%、100% epochs 运行小型 milestone 对局，画出我们自己的训练中胜率曲线，但不拿这条曲线反选 checkpoint。

Target validation统一规则选 checkpoint；不看 engine test
→
Development batch相同 catalog、paired seats/seeds；报告差值与不确定性
→
Fresh confirmation胜者与 T0 用未使用 seeds 复测；package 不再调整

正式报告包括 W/L/error、completion、相对 T0 的 paired win-rate difference、置信区间、先后手和 per-opponent 结果。单次点估计提升只算 exploratory；辅助构筑不参加正式强度评估。
