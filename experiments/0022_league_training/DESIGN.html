0022 League Training

当前阶段：吞吐 feasibility 已实测；end-to-end gate 通过，opponent-only 2.0x gate 待优化；正式 PPO 尚未开始。

目标是在 BC foundation 完成后，验证常驻、批量化 opponent pool 是否能显著提高真实 RL rollout 与迭代吞吐，同时用一个不会随训练漂移的 Frozen League 保持质量锚点。

核心结论

Frozen pool

16 个完整冻结策略：exact deck、共享 Encoder、Decoder/Value、checkpoint、package 和 engine hash 全部固定。它们是质量锚点，不只是 Frozen Encoder。

Live pool

16 个 deck-specific Decoder/Value 分支，共享长期冻结的 source-free Encoder。每个 policy 只从自己的 actor trajectory 和终局 reward 更新。

吞吐目标

通过一个常驻 GPU inference service 批量执行共享 Encoder，再按 policy_id 路由 Decoder，消除 per-game package load 和独立 CPU opponent inference。

研究边界

研究 Decoder-only 局部改进与 opponent throughput；不声称全局最优、完整 self-play equilibrium 或 CUDA battle engine parity。

所有正式对局继续由未修改 official engine runtime 执行。engine_cuda/ 在 semantic parity gate 通过前不能产生 0022 正式 rollout、reward 或强度结论。

模型和梯度所有权

组件是否训练职责
Shared source-free Encoder长期冻结卡牌、场面、资源、事件、exact deck 和 legal option 表示
Frozen Decoder/Value永不更新固定强度 anchor、回归指标和 historical snapshot
Live Decoder/Value按 deck 独立更新在现有表示空间中重新排序合法动作、ordered action 和 STOP
Official engine不修改合法动作、卡牌效果、随机结果、Prize 和终局判定

Frozen 对局中只有 Live/focal actor 的轨迹进入梯度。Live 对局中双方都可以更新，但必须分别保存自己的 observation、action、behavior log-prob、value、advantage、reward sign 和 policy version。

第一版 focal iteration

16 Frozen opponents × 10 games = 160 games
16 Live opponents   × 10 games = 160 games
                         total = 320 games / focal iteration

先后手使用固定平衡日程。每个 matchup 的 10 局只作 rollout 和快速诊断；正式趋势用跨 iteration 滚动窗口和 Wilson 区间。一个 focal deck 的 320 局不能冒充 16 个 deck 各自获得 320 局 actor 数据。

每场必须记录 actor_deck_id、actor_policy_version、opponent_deck_id、opponent_policy_version、seat、Frozen/Live role、pool snapshot、engine hash、reward 和 terminal reason。

BC 完成后的速度验证 gate

tuned CPU baseline → resident CPU service → resident GPU service

三臂必须使用相同 exact deck、checkpoint、official engine、完成局合同和先后手日程。分别记录 completed/error/unfinished、engine selections/s、opponent decisions/s、learner decisions/s、episodes/s、package-load、feature encode、IPC、H2D/D2H、latency、内存和 GPU utilization。

Promotion thresholds

  • opponent decisions/s 相对 tuned baseline 至少 2.0x；
  • end-to-end completed episodes/s 至少 1.5x；
  • 完成率、error 和 unfinished 合同无回归；
  • Frozen pool 固定 Arena 质量保持在预先记录的统计区间内；
  • profiling 证明收益来自常驻和批量推理，而不是减少局数或降低 opponent 质量。

只有 policy inference 变快、但 end-to-end rollout 没有提升时，不能称为 RL iteration speedup。

2026-07-31 PPO-ready 实测：A sample 300 局为 1.990 episodes/s、339.14 selections/s；unified stacked GPU D 512 局为 3.568 episodes/s、582.17 selections/s、264.44 opponent decisions/s，完成率均 100%，trajectory log-prob/entropy/value 非有限数均为 0。end-to-end 1.79x 通过，opponent-only 1.73x 尚未达到 2.0x，因此仍不能开始 Live self-evolution。

Live policy 不自动进入 Frozen pool。晋级必须创建新版本，完成 package validation、固定 Frozen/historical evaluation、pool snapshot 审计和权威 HTML 报告。

16-deck catalog 准入

第一版设计不写死 16 套具体卡组。正式 catalog 是独立、不可变、带 hash 的信息资产。每个候选必须：

  • 拥有可审计的 exact 60-card deck，来自线上环境或官方 submission/Episode 身份链；
  • 在当前线上环境真实出现且频率足够，不按 archetype 名称猜测构筑；
  • 在 BC 数据中有可追溯的关键卡牌和构筑语义覆盖；
  • 通过 package、deck hash、card ontology 和 official engine validation；
  • 覆盖不同的进化、攻击、控制、资源、Prize race 和接力模式，避免 16 个近似 deck；
  • 记录来源、频率、选择理由、BC coverage 和风险。

新卡牌、定向 card embedding 或开放 Encoder/adapter 是验证第一版 League 可行后的独立实验，不能无记录地混入第一版 catalog。

风险与护栏

共同退化

保留 zero-shot Frozen、historical best 和固定外部 anchors；Live-only 胜率不晋级。

策略循环

报告 cross-play matrix、先后手、Frozen anchor 和历史 snapshot，不只看平均 Elo。

稀疏 reward

主合同保持 terminal win/loss；记录 value calibration、优势、KL、探索和 episode length。

吞吐假象

完成率、对局合同和 opponent 质量必须一致；减少游戏或忽略 error 不算加速。

版本和成功标准

正式版本使用 rl_runs/0022_league_training/versions/V<n>_<tag>/，并在 experiments/0022_league_training/evaluation/ 保存权威报告。每个版本记录 BC、Encoder/Decoder schema、Frozen/Live pool、deck/engine hashes、sampling weights、先后手、W&B identity 和吞吐。

0022 第一阶段成功不要求全局最优：它需要证明相同质量下真实 RL throughput 显著提高，并证明 Decoder-only policy 能相对 zero-shot/Frozen anchor 获得稳定、可追踪的局部改进。
